# Validation gates для перехода от words к pose_words

## 1. Назначение документа

Этот документ фиксирует формальные validation gates, по которым команда может принимать решение о снижении роли `words` в пользу `pose_words`.

Он дополняет `ADR-001`, но не заменяет его:
- `ADR-001` фиксирует архитектурное направление;
- этот документ фиксирует проверяемые условия, при которых это направление можно считать практически подтвержденным.

До прохождения этих критериев `words` остается baseline/reference pipeline. Наличие выбранного целевого направления само по себе не означает, что `words` уже можно заморозить, убрать или перевести в неактивный статус.

Техническая валидация воспроизводимого non-dummy validation path отдельно зафиксирована в `docs/pose_words_technical_validation.md`.

## 2. Связь с текущими архитектурными решениями

В `ADR-001` уже зафиксировано, что `pose_words` является целевым основным pipeline для распознавания слов, а `words` сохраняется как временный baseline/reference pipeline.

Этот документ не меняет указанное решение. Он задает условия, при которых команда может перейти от архитектурного выбора к практическому выводу о том, что `pose_words` достаточно подтвержден для снятия `words` с активной основной роли.

## 3. Принцип принятия решения

`words` не снимается с основной роли по субъективному ощущению или по факту наличия `ADR-001`.

Решение принимается только после прохождения обязательных validation gates. Если хотя бы часть ключевых gates не пройдена, `words` сохраняется как baseline/reference pipeline.

## 4. Набор validation gates

### Сводка по текущему состоянию

| Gate | Краткое название | Текущий статус |
| --- | --- | --- |

### VG-01. Реальные, а не dummy, pose/BIO артефакты

- Почему этот gate важен: `pose_words` нельзя считать подтвержденным основным pipeline, если runtime опирается только на bootstrap/dummy модели, предназначенные для восстановления контура без падения, а не для реального распознавания.
- Что считается условием прохождения: в репозитории или в поддерживаемом внешнем артефактном хранилище существуют реальные артефакты для `pose_word` classifier и BIO segmenter; они не помечены как dummy/bootstrap; их происхождение, датасетный контекст и роль в runtime понятны.
- Какие артефакты/доказательства должны существовать: актуальные `pose_word_model.onnx`, `pose_word_labels.txt`, `pose_word_config.json`, `bio_segmenter.onnx`, `bio_thresholds.json`, `bio_config.json`, а также метаданные training/export происхождения или отчет о происхождении артефактов.
- Как проверяется gate: проверяются активные артефакты и их JSON-метаданные; в конфиге и документации не должно быть указаний, что runtime использует `make_dummy_*` или bootstrap baseline вместо реальных моделей.
- Текущий статус по репозиторию: **выполнен**.

Основание: в репозитории есть воспроизводимый validation path `backend/scripts/run_pose_words_validation.py`, который реально обучает обе модели и экспортирует non-dummy ONNX-артефакты в `backend/artifacts/validation/pose_words/`. Также появился официальный install/promote workflow `backend/scripts/install_pose_words_runtime_artifacts.py`, который валидирует metadata source artifacts, делает их active runtime set в `backend/artifacts/runtime/active/pose_words/` и пишет `backend/artifacts/runtime/active/pose_words/pose_words_active_manifest.json`. Фактический прогон зафиксирован в `docs/pose_words_technical_validation.md`: backend реально стартует на active non-dummy artifacts, а `/health` явно показывает `active_artifact_profile=validation_active`, `pose_words_artifact_kind=validation`, `bio_artifact_kind=validation`, `pose_words_non_dummy_active=true`. Dummy/bootstrap path сохраняется, но больше не является единственным active runtime path.

### VG-02. Воспроизводимый путь train/export/inference

- Почему этот gate важен: если `pose_words` нельзя воспроизвести с нуля, то перевод `words` в неактивный статус создаст операционный и инженерный риск.
- Что считается условием прохождения: существует понятный и документированный путь `train -> export -> runtime use` для `pose_word` classifier и BIO segmenter без скрытой зависимости от локальной машины конкретного разработчика.
- Какие артефакты/доказательства должны существовать: скрипты подготовки датасета, скрипты обучения, скрипты экспорта, runtime runbook, ожидаемые выходные артефакты, а также подтверждение, что этот путь действительно собирает используемые runtime-файлы.
- Как проверяется gate: на чистом окружении или в CI воспроизводится полный путь от подготовленного датасета до запуска backend с полученными артефактами.
- Текущий статус по репозиторию: **выполнен**.

Основание: в репозитории теперь есть единый runner `backend/scripts/run_pose_words_validation.py`, который проходит путь `synthetic_fixture -> train -> export -> runtime use -> backend smoke -> report` без скрытых локальных ручных шагов. Фактический прогон зафиксирован в `docs/pose_words_technical_validation.md`: были реально обучены `pose_word` classifier и BIO segmenter, экспортированы ONNX-артефакты и сформирован machine-readable report. Это закрывает gate именно на уровне технической воспроизводимости validation path; оно не означает подтверждения product-grade training path на большом реальном датасете.

### VG-03. Корректный runtime-запуск `pose_words`

- Почему этот gate важен: целевой pipeline должен запускаться как рабочая сервисная часть, а не только существовать в виде кода и отдельных модулей.
- Что считается условием прохождения: backend стартует в режиме `pose_words`, сегментация включается через ожидаемую конфигурацию, сервис не падает на базовом запуске, сценарий старта понятен и документирован.
- Какие артефакты/доказательства должны существовать: актуальный runtime config, health/readiness логика, runbook запуска, тест или smoke-проверка на базовый старт и readiness.
- Как проверяется gate: backend запускается по задокументированному сценарию, затем через `GET /health` подтверждаются `recognition_mode=pose_words`, `segmentation.enabled=true` и корректный readiness-статус.
- Текущий статус по репозиторию: **выполнен**.

Основание: `backend/config.yaml` уже настроен на `recognition_mode: pose_words` и `segmentation.enabled: true`; сценарий запуска описан в `backend/README.md`; readiness-логика реализована в `backend/app/main.py`; `backend/tests/test_artifacts_bootstrap.py` фиксирует корректные состояния `/health` при отсутствии и наличии обязательных артефактов.

### VG-04. Smoke/integration проверка на рабочем контуре

- Почему этот gate важен: между наличием runtime-кода и минимальной интеграционной жизнеспособностью есть разница; нужен хотя бы один повторяемый сценарий, который проходит основной путь обработки до наблюдаемого результата.
- Что считается условием прохождения: существует smoke check, runbook или интеграционный сценарий, позволяющий проверить `pose_words` на рабочем контуре от входного кадра до payload/результата; результат такого прогона фиксируется наблюдаемым образом.
- Какие артефакты/доказательства должны существовать: smoke-скрипт или integration test, runbook запуска, лог или отчет о прогоне, который можно повторить.
- Как проверяется gate: поднимается backend, запускается smoke-сценарий, проверяются `/health`, WS-поток, наличие `pose_words` payload, сегментов и итогового JSONL-лога или аналогичного артефакта.
- Текущий статус по репозиторию: **частично выполнен**.

Основание: в репозитории есть `backend/scripts/smoke_pose_words.py`, `backend/scripts/smoke_pose_words_segmentation.py`, runbook в `backend/README.md`, интеграционный тест `backend/tests/test_pose_words_integration_smoke.py` и новый reproducible runner `backend/scripts/run_pose_words_validation.py`. Фактический validation run подтвердил backend startup в `pose_words`, readiness на non-dummy validation artifacts и direct runtime replay до результата. При этом backend WebSocket smoke по-прежнему использует mock JPEG frames и в зафиксированном прогоне не дал положительных segment/commit событий, поэтому gate остается частично выполненным, а не полностью закрытым.

### VG-05. Понятный контракт входа/выхода для интеграции

- Почему этот gate важен: если `pose_words` становится основным pipeline, внешние слои должны использовать его по явному контракту, а не по неформальным договоренностям, зашитым в код frontend/backend.
- Что считается условием прохождения: понятны входы и выходы pipeline, есть явные контрактные ожидания для runtime payload, а интегрирующий слой может использовать `pose_words` без угадывания скрытых правил.
- Какие артефакты/доказательства должны существовать: кодовые схемы или builders payload, contract tests, документ или схема, описывающая обязательные и optional поля, а также правила совместимости.
- Как проверяется gate: сверяются фактические поля payload, тесты контракта и документация; изменения контракта должны быть отслеживаемы и не ломать frontend молча.
- Текущий статус по репозиторию: **частично выполнен**.

Основание: фактический WS payload собирается через `backend/app/schemas.py`, контракт частично закреплен тестами `backend/tests/test_ws_contract.py`, а `docs/current-state.md` описывает обязательный каркас payload и optional поля `pose_words`. При этом `docs/target-architecture.md` отдельно фиксирует, что явного версионируемого слоя контрактов сейчас нет и рекомендует отдельный `docs/ws-contract.md`.

### VG-06. Сравнение `pose_words` с `words` как baseline

- Почему этот gate важен: baseline нельзя выключать без сравнения с baseline; иначе переход будет опираться на архитектурную гипотезу, а не на проверяемое сравнение.
- Что считается условием прохождения: существует хотя бы один зафиксированный сравнительный сценарий `pose_words` против `words`, определены критерии сравнения и команда может аргументированно сказать, не ухудшается ли система по ключевым параметрам.
- Какие артефакты/доказательства должны существовать: сравнительный runbook, единый набор входных сценариев, критерии сравнения и сохраненный отчет по качеству, latency, устойчивости или другим согласованным метрикам.
- Как проверяется gate: обе ветки запускаются на одном и том же сценарии, после чего результаты сравниваются и фиксируются в документе, отчете или версионируемом артефакте.
- Текущий статус по репозиторию: **не выполнен**.

Основание: в архитектурных документах есть только требование сохранять `words` как baseline/reference и использовать его для сравнения, но в репозитории не найден зафиксированный сравнительный сценарий, итоговый сравнительный отчет или единый evaluation-артефакт для `pose_words` против `words`. Наличие `backend/tools/eval_realtime_log.py` не закрывает этот gate, потому что это точечный инструмент, а не оформленное baseline comparison.

### VG-07. Базовая стабильность и пригодность для demo/integration

- Почему этот gate важен: даже перспективный pipeline нельзя делать основным путем, если он нестабилен, непредсказуем или регулярно ломает demo/integration контур.
- Что считается условием прохождения: pipeline достаточно стабилен для демонстрационного и интеграционного использования; отсутствуют известные критические блокеры, делающие его непригодным как основной путь распознавания слов.
- Какие артефакты/доказательства должны существовать: результаты повторяемых smoke-прогонов, журнал известных блокеров, ручные demo/integration прогоны или краткий отчет по стабильности на согласованных сценариях.
- Как проверяется gate: выполняется серия ручных или полуавтоматических прогонов на целевом runtime-профиле, после чего документируются наблюдаемые сбои, деградации и блокеры.
- Текущий статус по репозиторию: **требует ручной проверки**.

Основание: в репозитории есть health/smoke-механизмы и локальные integration tests, но нет зафиксированного набора повторяемых demo/integration прогонов, по которым можно утверждать стабильность на целевом контуре. Документы подтверждают наличие работающего runtime, но не дают достаточного доказательства эксплуатационной устойчивости как основного пути.

### VG-08. Документация достаточна для поддержки pipeline

- Почему этот gate важен: основной pipeline нельзя поддерживать только за счет знания отдельных разработчиков; документация должна позволять запустить, понять и сопровождать `pose_words`.
- Что считается условием прохождения: README, backend docs, config docs и архитектурные документы согласованы между собой; понятно, как использовать `pose_words`; нет критического разрыва между фактической архитектурой и документацией.
- Какие артефакты/доказательства должны существовать: согласованные архитектурные документы, runbook запуска, artifact docs, описание роли `words` и `pose_words`, а также актуальные ссылки между этими документами.
- Как проверяется gate: проверяется, можно ли по документации понять назначение pipeline, required artifacts, сценарий запуска, базовые ограничения и критерии готовности без обращения к устным пояснениям.
- Текущий статус по репозиторию: **частично выполнен**.

Основание: в репозитории уже есть `README.md`, `docs/current-state.md`, `docs/target-architecture.md`, `docs/adr/ADR-001-pose-words-target.md`, `backend/README.md`, `backend/docs/pose_words_artifacts.md`, этот документ и `docs/pose_words_technical_validation.md`. Эти документы теперь согласованно описывают draft-статус репозитория, роли `letters` / `words` / `pose_words`, active non-dummy runtime path и сохранение bootstrap path как fallback. При этом gate остается частично выполненным, потому что явного версионируемого contract document по-прежнему нет, а часть локальных backend planning docs частично устарела относительно текущего train/export и runtime wiring.

## 5. Обязательные и вспомогательные gates

### Обязательные gates для снятия `words` с основной роли

- `VG-01` Реальные, а не dummy, pose/BIO артефакты.
- `VG-02` Воспроизводимый путь `train -> export -> runtime use`.
- `VG-03` Корректный runtime-запуск `pose_words`.
- `VG-04` Smoke/integration проверка рабочего контура.
- `VG-05` Понятный контракт входа/выхода для интеграции.
- `VG-06` Сравнение `pose_words` с `words` как baseline.
- `VG-07` Базовая стабильность и пригодность для demo/integration.

Эти gates являются stop-факторами для решения о переводе `words` в `frozen`/`deprecated`/`baseline-only` статус. Пока хотя бы один из них не пройден, `words` должен оставаться активным reference pipeline.

### Вспомогательные gates

- `VG-08` Достаточность документации для поддержки pipeline.

Этот gate не должен подменять собой техническую готовность, но он обязателен перед фактическим долгосрочным сопровождением `pose_words` как основного пути и особенно важен перед окончательным удалением `words` из репозитория.

## 6. Правило принятия итогового решения

`words` можно переводить в `frozen`/`deprecated`/`baseline-only` состояние только после прохождения всех обязательных gates из раздела 5.

До этого `words` остается reference pipeline. Сам по себе факт наличия `ADR-001` не является достаточным основанием для удаления `words`, отключения его активной поддержки или трактовки `pose_words` как доказанно готового эксплуатационного replacement.

Полное удаление `words` из репозитория целесообразно рассматривать только после прохождения обязательных gates и приведения сопровождающей документации в согласованное состояние.

## 7. Текущее состояние по итогам анализа

### Краткий итог

- Выполнены: `VG-01`, `VG-02`, `VG-03`.
- Частично выполнены: `VG-04`, `VG-05`, `VG-08`.
- Не выполнен: `VG-06`.
- Требует ручной проверки: `VG-07`.

### Управленческий вывод

По текущему состоянию репозитория `pose_words` подтвержден как архитектурное целевое направление, но не подтвержден как достаточная замена для снятия `words` с активной baseline-роли.

Главные блокеры на данный момент:
- положительное end-to-end распознавание через backend WebSocket на camera/video контуре не зафиксировано как пройденный reproducible smoke;
- отсутствует оформленное baseline comparison `pose_words` против `words`;
- стабильность на demo/integration контуре не зафиксирована как пройденная ручная валидация.

Следовательно, на текущем этапе `words` должен оставаться reference pipeline, а `pose_words` — целевым направлением, проходящим последовательную валидацию по описанным gates.
